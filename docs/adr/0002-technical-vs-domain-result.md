# ADR-0002. Технический HTTP-результат и предметный outcome

- Статус: принято
- Дата: 2026-08-25

## Контекст

Один generic-маршрут `POST /api/{module}/{action}` обслуживает и технические отказы runtime, и предметный успех PostgreSQL-функции. Если смешать эти уровни, автопроверка и клиент не смогут отличить:

- «маршрута нет» от «операции нет»;
- повтор идемпотентного запроса от новой операции;
- ошибку контракта от контролируемого отказа target.

Нужно явно развести HTTP-конверт runtime и envelope, который возвращает `api.invoke` / предметная функция.

## Решение

### Предметный результат (domain)

Его формирует PostgreSQL:

- `status`: `ok` или `error`;
- при успехе — `outcome` из манифеста (`CREATED`, `FOUND`, …) и `result` по `response_schema`;
- при контролируемом отказе — код вроде `operation.not_found` или `idempotency.conflict`.

Целостность тоже предметная: уникальный индекс идемпотентности, атомарность `operations` + `OPERATION_CREATED`, неизменяемость опубликованного манифеста.

C# не дублирует эти инварианты своими locks и не выбирает target из payload.

### Технический результат (HTTP)

Его формирует runtime после проверки JWT, schema и транзакции:

- HTTP-статус и `retryable` по матрице `contracts/course-1`;
- единый JSON-конверт `status=ok|error`;
- `meta.correlationId` после успешной аутентификации; до неё — `null`;
- `meta.actionVersion`, если версия резолвилась.

Правило commit: транзакция фиксируется только если invoke вернул `status=ok`, `outcome` входит в манифест, а `result` проходит `response_schema`. Иначе полный rollback. Повтор идемпотентного ключа с тем же payload возвращает исходный предметный envelope и HTTP 200: второго эффекта нет.

Особый случай `operation.get`: неизвестный `operationId` — предметная ошибка `operation.not_found` (HTTP 404), а не `action.not_found` и не 500.

### Что не считается предметным успехом

- неизвестный или выключенный action;
- неверный JWT / тип claim;
- payload вне schema;
- неизвестный `outcome` или `result` вне `response_schema`;
- недоступность PostgreSQL и истечение `timeout_ms`.

Это технические отказы runtime. Target либо не вызывается, либо его побочный эффект откатывается.

## Следствия

- Клиент всегда видит один формат тела; смысл кода ошибки читается из `code`, а не из произвольного текста фреймворка.
- OpenAPI строится из манифестов: технический путь один, предметные поля живут в `request_schema` / `response_schema`.
- Логи содержат `correlationId`, маршрут и статус. JWT, payload и SQL в журнал не пишутся.
